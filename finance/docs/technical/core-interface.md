# 技术设计：核心插件业务 Interface

状态：接口设计提案，未实现或验证；以下名称是本项目候选名，不是 DSH 内置接口。最终传输方式需通过 DSH 集成验证确定。

依据：[统一草稿与提交校验](drafts-and-posting.md)、[双插件架构](architecture.md)。遵循 codebase-design 的深模块原则：调用者表达业务任务，由核心封装字段校验、关系分配、重复判断和一致性处理。

## 1. 共同契约与两个入口

finance-core 提供一套业务 Interface；UI Adapter 与 Agent 工具 Adapter 都调用该 Interface。输入描述业务意图，输出说明业务结果，不让调用者自行操作数据库或拼接分录。

工具可以为了模型使用便利包装成记一笔、查明细、看汇总等任务，不必与每个核心方法一一对应，也不能形成一套独立账务逻辑。

UI 与 Agent 不直接改余额、不自行结清借款、不以本地筛选替代核心账本归属检查。表单查询不经过模型；大文件解析可直接由核心任务运行，Agent 不必逐行调用记账。

## 2. 候选能力组

| 能力 | 候选名称 | 主要输入 | 返回 |
| --- | --- | --- | --- |
| 创建或修订操作提案 | prepareOperation | 账本、类型化操作意图、事实/证据、目标版本 | 提案标识/版本、影响预览、问题、允许动作 |
| 应用提案 | applyOperation | 提案标识/版本、幂等标识 | 已保存业务结果与各口径金额变化，或冲突/需核对 |
| 查看操作结果 | getOperation | 操作标识、账本 | 执行状态、结果及受影响记录 |
| 提交导入资料 | startImport | 已登记资料引用、目标账本、来源提示、幂等标识 | 持久化任务标识 |
| 查看或控制导入 | getImport / cancelImport | 任务标识、账本 | 分组摘要、进度、草稿、取消状态 |
| 处理核对项 | resolveIssue | 问题及版本、类型化处理选择、证据 | 更新后的提案与影响预览 |
| 查询业务数据 | queryFinance | 有限查询类型、类型化筛选、分页/快照 | 明细/余额/往来/计划等及依据 |
| 分析与预测 | analyzeFinance | 期间、范围、明确口径、认知版本、可选场景 | 数值、构成、限制与明细定位 |

这些是能力分组，不宣称八个万能方法足以完整表达所有业务。queryFinance 使用受约束的查询类型，不接受任意 SQL 或模型生成执行代码。prepareOperation 使用区分类型的输入结构，不是任意 JSON 修改器。

大批次评估和应用可返回任务标识，使用同样的任务查询约定；不能假定每个调用同步完成。批次提交通过提案/提交能力复用共同业务规则，不另建绕过校验的快速入库路径。

## 3. 操作意图

候选意图包括：记录收支、修订账目、补充来源、确认同一交易、建立退款分配、结算往来、调整分类标签、归组事项，以及账户/预算/规则等明确业务设置。

对象所需输入随意图不同。例如“结算借款”需已有往来及分配金额，“修改分类”不要求调用者重复提交金额日期等全部字段，避免覆盖未修改事实。

核心可以把多个意图组成一个一致操作单元；原子执行范围由依赖决定，不能让调用者任意拆开转账两端或重复关联的一组记录。大批次按独立单元分别记录结果。

## 4. 调用上下文与权限来源

每个请求有明确账本。身份、调用入口与权限来自可信宿主上下文，不能由 Agent 在参数里自称管理员或填 confirmed=true。

用户明确输入、用户配置默认、已接受规则和模型候选在证据中区分。resolveIssue 的“确认”必须记录真实动作来源；Agent 选了一个关系不等于用户已确认。只有明确业务规则允许的自动处理才可由 Agent 发起并由核心检查。

当前家庭共享暂缓，仍在核心校验账本与对象归属。未来授权设计可接入，不以多个 DSH 会话等同独立用户身份。

## 5. 提案与提交

prepareOperation 可保存草稿/提案，但不改变正式账务；返回精确影响，包括消费、资金账户、往来未结以及仍然未知的部分。核心保存提案内容，提交引用它而非接受调用者重传一份未经核验的影响列表。

applyOperation 在执行时重新检查提案版本、相关对象版本、规则版本、来源唯一性和金额约束。预览已过期时返回冲突与重新评估入口，不能按旧结果盲写。

校验重点为相关记录与规则版本，不因账本里任意一笔无关记录变化就让全部提案失效。涉及分类规则批量修改、汇总条件批量操作时需冻结目标集或携带查询快照，避免预览 10 笔、实际修改 12 笔。

是否要求用户点击确认由已配置业务策略决定；两阶段核心契约不意味着 UI 要显示两次确认。清晰单笔可以由 Adapter 连续 prepare/apply，遇阻断即返回问题。策略当前仍是提案，不能据此绕过未知字段和重复判断。

## 6. 重复请求与并发

幂等标识的作用域包含账本与操作类别，并绑定规范化请求内容。相同标识相同内容返回同一结果；相同标识不同内容返回明确冲突，不能无条件复用旧结果。重试保持标识，用户另一笔真实同金额交易使用新标识。

结果与正式账务变更在同一提交单元内持久化；客户端超时后通过操作标识查询，不先认定失败再以新标识提交。解析任务的启动和财务写入各自有幂等契约。

并发预览都判为新增时，最终提交仍检查已登记的来源。来源交易编号结合渠道、账户/来源归属范围判断，不对金额日期设置唯一约束。无充分标识的模糊重复需要核对，不承诺算法能完全识别。

## 7. 核对项不是任意打补丁

问题返回稳定代码、涉及字段、业务影响、依据、可用处理选择和版本。例如账户待定可选择真实账户或按允许策略暂不归属；重复候选可确认同笔或明确不同交易。

resolveIssue 重新生成提案，选择改变金额关系时重新显示影响。不能通过把问题标成已读使其绕过必要校验。用户驳回候选与系统隐藏提示分别表达。

## 8. 查询与分析契约

queryFinance 支持交易、来源、账户、往来、核对项、计划及设置等明确查询类型。返回分页游标、数据版本和账本范围。大量交易不能全部塞进模型上下文。

analyzeFinance 返回使用范围、业务期间、认知截止时间或修订号、口径、金额指标、未定金额、覆盖限制和明细定位。先做汇总，再按需要获取细分与明细。分类/标签统计是否重叠必须明确。

在同一次多步分析中固定数据快照或检测版本变化：如果无法一致读取，不把旧总额和新明细拼成一份结论。历史回放能力需存储设计支持；在未具备时明确拒绝该模式或只返回已保存报告，不伪装可重现。

报表明细引用使用账本/记录等稳定业务引用，由 UI 映射导航，不让核心或 Agent 臆造 URL。标签重命名、事项归组不应让历史来源定位失效。

## 9. 导入任务与变更通知

任务状态至少区分排队、运行、待核对、完成、部分完成、失败、取消中/已取消等实际含义；最终枚举在任务模型统一。getImport 返回各阶段计数和每个独立单元结果，不能仅一个百分比掩盖已提交内容。

cancelImport 停止未完成工作，不自动撤销已提交账目。任务执行状态与提案/账目状态分开。

UI 可订阅导入进展、核对项变化和账目变更通知，但通知不是唯一事实来源。重复通知通过版本/序号处理，断线后重新查询；不能以收到事件数量计算余额。事件机制及 DSH 接入留待验证。

## 10. 更正与撤销

更正通过指向原记录的类型化提案表达。撤销引用原操作，核心先评估当前依赖，再生成可执行更正方案，复用 prepare/apply；不提供任意删除数据库行的工具。

仅补来源的操作撤销后保留原手工账目。已被还款、退款或后续编辑依赖的记录不能无条件恢复旧快照；返回受影响关系并要求重新评估，而不是静默级联删除。

历史操作和证据继续保留。不可逆外部支付不属于当前 Interface，本方案的撤销只涉及账本及其关系。

## 11. 错误契约与性能

错误建议包含 code、用户可理解的 message、字段/记录引用、可执行处理选择、是否适合原请求重试。暂定类别：输入缺失或冲突、格式/币种不支持、账本归属错误、重复候选、分配超额、版本冲突、幂等内容冲突、任务失败。

输入与版本冲突不能无限自动重试；运行故障只在契约允许且幂等标识不变时重试。发生部分成功时返回已完成结果，不把整个批次表现为全失败。

普通查询分页、导入和大型分析可异步返回任务；超时不等同取消。具体时延目标、最大文件量和模型调用成本待代表性样本验证，不提前承诺数值。

## 12. 示例调用路径

自然语言“午饭 35 元”：Agent 提出消费意图 → prepare 返回账户待补和消费影响 → 若策略允许则 apply → 返回账目标识和待补项。

后来导入同笔来源：startImport → 解析匹配产生补来源提案/核对项 → 用户或明确规则解决候选 → apply 只补来源与缺失信息 → 消费不增加。

用户问“本月为何多花”：analyze 固定口径给出差额 → 查询构成明细 → Agent 解释并引用。查询不顺带改分类；需要修改时单独进入操作流程。

## 13. 后续验证

从共同 Interface 验证同输入经 UI/Agent 得到一致结果；幂等同内容重试和不同内容冲突；并发写入；预览过期；金额分配守恒；部分信息补全；受依赖撤销；跨账本请求；多步查询版本一致；任务取消部分成功；模型不能伪造确认来源。

不编写只验证内部方法调用次数的镜像测试。下一步对象模型要明确来源、账目、影响、关系分配、提案、操作结果与任务各自职责，再设计存储事务。
