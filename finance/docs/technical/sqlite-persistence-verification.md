# 跨来源匹配的 SQLite 隔离验证

日期：2026-09-24。状态：**合成技术实验通过，正式存储方案未冻结**。运行环境为本机 Windows、Python 3.11.15、SQLite 3.53.1；不涉及 DSH、实际微信账单或银行截图。问题是[来源匹配方案](source-identity-and-matching.md)中的同订单关联、去重和独立批次单元，在持久化、两进程竞争及中途退出时能否保持一份有效金额。

## 复现

在仓库根目录运行：

```powershell
python .\experiments\finance-sqlite-probe\verify.py
```

[实验代码与说明](../../../experiments/finance-sqlite-probe/README.md)使用 Python 标准库 `sqlite3`。每次运行建立新的本地临时数据库，位于被忽略的根 `.runtime/`；不读取或提交真实金融资料。实验把同一已验证作用域的订单设为单个相关单元，在 `BEGIN IMMEDIATE` 事务内检查来源唯一性、相容事实、事件金额、重复提醒及单元结果；独立订单组分别提交。

## 运行结果

| 场景 | 观察结果 |
| --- | --- |
| 同订单微信消费 35 元与银行卡扣款 35 元 | 一笔事件、两份来源；消费 `3500` 分、银行卡 `-3500` 分 |
| 同一批次请求重试 | 返回已持久化结果，不新增事件或提醒；相同批次标识换内容被拒绝 |
| 新批次重导相同来源 | 两条来源跳过，产生两条可见提醒记录；金额不变 |
| 两个进程同时提交同一订单 | 两个进程均成功结束；最终一笔事件、两份来源、`3500/-3500` 分，后到批次只记重复提醒 |
| 写入事件及来源后、提交前强制退出 | 退出码 77；重开数据库后没有该事件、来源或单元结果；原批次标识重试成功 |
| 第一独立单元已提交，第二单元写入时退出 | 第一单元的 2000 分消费保留，第二单元回滚；整批重试后消费 5500 分、银行卡 -3500 分，第一单元未重复执行 |
| 同订单另一来源日期不清 | 该订单组留下可追溯的待核对输入；同批另一独立订单的 2000 分消费先提交 |
| 相同编号文本但不同作用域 | 保留两笔单来源事件，不自动建立同笔关系 |

实验断言及 Python 语法检查通过。结果支持**相关单元原子提交、独立单元部分成功、持久化幂等结果与重启恢复**这一设计方向；它不等于正式数据库选型已批准。

## 边界与后续

输入是可信的合成归一化对象，`order_verified` 由实验预设；真实个人微信导出和银行截图是否共享同一订单号仍无证据，见[输入字段证据](input-field-evidence.md)。实验只覆盖普通消费与银行卡扣款；未验证跨日期结算、退款/报销等后续依赖、两个旧正式账目的迁移、备份恢复、数据库迁移、磁盘故障、较高并发量及 DSH 插件接入。两进程竞争是一次受控运行，不能推断生产并发性能。

下一轮应先用脱敏样例确定实际字段作用域；样例缺席时可继续验证正式 Interface 与 DSH 文件导入链路，但不得把合成订单号规则默认启用于未知来源格式。存储方面还需设计任务与原始文件生命周期、备份恢复和版本迁移，之后才能决定是否采用 SQLite 作为正式实现。
