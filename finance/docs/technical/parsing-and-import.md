# 技术设计：多入口解析、导入与记账

状态：根据已确认输入完善的候选技术方案，未实现或验证。具体库、模型及接口名称尚未选定。

需求依据：[导入、单笔记账与核对](../requirements/import-and-reconciliation.md)。

## 1. 已确认输入

- 微信、支付宝：CSV 和 Excel；表头名称及布局可能变化。
- 银行：主要为截图；一张可能包含单笔详情或多条流水。
- 自然语言：独立记账入口，允许一段话生成一条或多条草稿。
- 单笔表单：直接输入金额、类型、日期、账户、分类等，不必调用模型。

截图不是推迟的附属格式。PDF、银行结构化文件等可保留扩展，不假定当前必须实现。Excel 的具体扩展名、导出样式与实际文件需后续样例确认。

## 2. 统一入账链路

文件解析 / 截图提取 / 自然语言理解 / 表单输入 → 带来源与不确定性的记账草稿 → 共同业务校验 → 重复候选与关系核对 → 提交账目 → 可追溯结果。

草稿是各入口的统一中间表达，不强迫文件行、用户记账和银行卡流水一一对应。批次只是多个草稿的处理容器，单笔输入不需要假装上传文件。

来源事实与正式账目分离。一个账目可以关联多份来源，也可以暂时只有用户输入依据。更正人工账目不修改原始文件；补充来源不自动新增一笔消费。

所有入口共享核心提交能力，避免聊天与 UI 分别写数据库形成不同校验规则。事务、幂等与并发版本检查位于核心。具体命令和对象结构留待接口及模型设计。

## 3. CSV 与 Excel：结构识别和语义映射分开

先解析文件物理结构，再判断列的含义。文件类型识别不只信扩展名；CSV 需处理编码、分隔符、引号和多行字段；Excel 需处理多个工作表、空行、合并单元格及类型转换。订单号、卡号等按文本保留，防止前导零或长数字精度丢失；公式不作为可执行指令。

识别实际表头和明细区域，不假设第一行是表头；说明文字、导出摘要、合计行、重复表头与脚注不能变成交易。表头名称、列值形态和交易行结构共同参与识别。

语义映射建议分层：

1. 已验证来源样式和映射版本。
2. 归一化表头与同义词规则，结合列值校验候选含义。
3. 未知或歧义结构由模型提出字段映射建议，经校验及必要核对后执行。

规则不能仅根据名称猜测；同一文件可能同时有交易时间和入账时间、消费金额和余额。样式匹配后仍逐批验证关键字段，表头未变也可能语义变化。

新增可选列、列顺序变化尽量自动适配；关键列缺失或金额方向矛盾需停在待核对。映射提案记录样例、依据、来源和版本，不把模型输出立即发布为所有文件的通用规则。

模型主要辅助理解结构与歧义，不要求其重新输出整份已能确定性解析的表格。原始行、原始列值与映射结果均可追溯。

## 4. 银行截图：提取与校验

候选路径是 OCR/版面提取加语义解析，或直接使用视觉模型输出结构化结果；需要用实际截图比较准确性、来源定位、成本和失败方式，不在没有实验时预定某一种。DSH 的模型能力不自动等同于图片识别能力，需验证实际提供者或工具。

保留原图引用与字段所在区域，用户可把金额、日期和账户结果与图片对应检查。区分单笔详情、流水列表、余额页、通知截图；一次上传多张时检查重复、重叠列表及裁切行。

不假设红色一定是支出、余额变化一定对应可见交易，也不按图片上传顺序推断完整时间线。年份缺失、日期标题被裁切、金额不清、仅有遮罩卡号等都保留不确定性。

金额、收支方向、日期、交易状态和账户是重点核对字段；模型置信分不能替代来源证据。没有连续完整流水时不以余额差强行补一笔交易。

截图中明确银行转账仅证明资金变动，不能自动认定是消费、还款或报销。同金额相近时间的多笔交易不自动合并。

## 5. 自然语言与表单

自然语言通过 DSH Agent 调用受约束的草稿/提交工具；表单直接调用同一业务能力。模型只提出解释，核心做金额、类型、账户及关系校验。

例：“昨天午饭 35，用微信付的。”可解析消费、餐饮、金额和相对日期；微信首先是支付渠道，不能默认为零钱账户。参考输入发生的时间与用户时区解释“昨天”，重试不重新按重试日计算。

缺账户时可保留账户待定的记账记录或草稿，具体产品策略待确认；不得计入某个虚构账户余额。用户已明确设置默认账户时可使用并展示默认来源。日期缺失同理，不能把默认值伪装成原文事实。

区分新增、查询与更正：“记午饭 35”是新增，“午饭记成 35 了，改成 30”应定位原记录后更正；歧义时不额外新增。还款等输入未拆明本金利息时，不凭猜测生成拆分。

清晰输入可考虑校验后直接记账并返回摘要及撤销入口；不确定输入只询问影响账务的必要信息。自动提交条件属于待定产品规则，不在技术方案里默认要求每笔确认。

## 6. 草稿需要表达的信息（候选，不是最终字段表）

账本与入口来源；金额/币种及方向；日期和精度；账户与支付渠道；交易状态；商户或对象；分类标签；原始来源定位；明确事实、规则推断、模型候选、用户确认的区别；校验问题与重复/关系候选。

导入来源的“交易状态”必须独立理解：失败、取消、待处理、退款中、部分退款、已完成等不是都能作为完成支付入账。原消费行显示已退款加独立退款行时，不能同时净额化再扣一次退款。状态映射按来源验证，来源状态变化可更新证据，不必新建消费。

正式账目可以是用户合并记账，多条付款可以匹配一个账目；支持部分金额分配，不以总额相同就确定对应。对象模型专题后续统一定义这些关系。

## 7. 去重与跨入口匹配

分开处理：同文件重导、同来源期间重叠、同来源状态更新、多渠道同笔支付、手工/自然语言账目与后导入流水匹配、截图重叠。

文件摘要只能证明文件相同；来源交易标识也需要结合来源和归属账户范围。组合指纹用于提出候选，不能把所有相同金额和日期当重复。

已确认的业务规则：同一文件重试，或来源机构、归属账户范围与稳定交易标识足以明确判定同一来源交易时，可自动跳过重复记录；处理痕迹和面向用户的提醒都必须保留。没有充分标识时仍只是重复候选，不把相同金额、日期当作自动跳过依据。提醒的具体呈现形式待 UI 设计。

例：先自然语言记午饭 35，后导入微信扣款 35，银行也有相应扣款。微信与银行若共享稳定订单号且其他事实不冲突，可按已确认规则自动关联；自然语言账目与这些来源之间仍需足够依据或用户确认。关联后不变成 105 元消费。若缺乏交易标识且同日有两笔 35 元，应保留候选，不自动合并。

订单号作用域、相容性检查、已入账两端的重复影响消除及并发复核见[来源身份与跨来源同笔匹配](source-identity-and-matching.md)。共同号不等于任意两个同形字符串；来源字段语义和资金路径须先验证。

关联来源时可以补充明确的支付时间或订单标识；不能无提示覆盖用户的分类、标签、合并金额或备注。用户账目与来源金额冲突时，展示差异并允许部分匹配/保持独立/明确更正。

## 8. 任务、提交与撤销

批次持久化处理状态、草稿版本、问题与映射版本。执行解析可以重试；写入使用幂等标识与事务，重复消息、点击和网络重试不能重复入账。幂等标识代表同一次操作，不能仅由金额和日期生成。

提交时检查预览对应的版本，过期时重新核对。已匹配到已有账目的导入只增加来源关联，撤销该批次时不应删除原手工账目。

撤销需区分本批新建账目、补充的来源、已被后续结算引用的关系，不能按批次盲删。已确认批量导入可先提交已核清的独立记录，让金额或日期不清的记录留待核对；有依赖记录的提交单元、部分失败后的重试、任务取消与后台继续运行规则仍待确定。

## 9. 插件职责的本专题约束

finance-core：来源解析、映射与规则版本、草稿校验、去重匹配、提交和变更记录；可封装视觉/OCR 提取能力，不与模型供应商绑定。

finance-ui：文件上传、截图对照、草稿表格、问题处理、单笔表单、提交结果与撤销入口。

DSH Agent：自然语言意图、字段映射候选、模糊关系建议与解释；通过同一核心能力操作账目。对来源文本只按数据处理，避免执行截图或备注中的指令。
