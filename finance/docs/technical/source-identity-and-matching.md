# 来源身份与跨来源同笔匹配

日期：2026-09-24。状态：**技术设计提案；合成内存实验已验证部分状态转移，尚未实现正式插件**。业务依据为[决策 D17—D19](../decisions.md)和[导入核对需求](../requirements/import-and-reconciliation.md)。本文细化[解析与导入](parsing-and-import.md)、[具体对象模型](concrete-object-model.md)及[核心业务接口](core-interface.md)，不预先冻结数据库表或 DSH 传输接口。

## 1. 三种不同的身份

| 身份 | 回答的问题 | 典型依据 | 处理结果 |
| --- | --- | --- | --- |
| 操作身份 | 这是否是同一次提交请求的重试？ | 账本、操作类型、幂等标识及请求摘要 | 返回原操作结果，不再执行写入 |
| 来源身份 | 这是否是已经处理过的同一份来源记录？ | 同文件内容及行位置，或来源机构、账户归属范围与稳定交易标识 | 明确重复可自动跳过、留痕并提醒 |
| 业务/资金身份 | 两份不同来源是否描述同一次支付及账户变动？ | 共享的稳定订单号、相容的金额和资金路径、无冲突的状态等 | 在安全条件满足时建立同笔关系；有效金额只计一次 |

三个检查依次进行，但不能互相替代。同一文件重传是来源去重；微信与银行各有一条来源、描述同一笔银行卡代扣，是跨来源关联。相同金额和日期只是检索线索，不是任何一种身份的唯一键。

## 2. 订单号的作用域

技术候选：解析器输出原始订单号、规范化值、字段语义及标识作用域。只有确认两份文件的字段指向**同一上游订单号体系**时，才能比较规范化值；两个渠道恰好都有 `12345` 不足以认定同笔。作用域映射须按来源样式版本保存依据，不让模型临时猜测的映射直接成为全局规则。

规范化只做已验证的无损处理，例如外部格式明确允许的空白清理；不截断前导零、不把长编号转为浮点数、不凭相似度或尾号匹配。来源机构、账户归属范围、原始值和映射版本始终保留。银行流水若只提供银行流水号而微信提供商户订单号，即使文本相同，也要先确认两者的语义是否可比。

## 3. 自动关联的判定流程

以下是实现 D19 的保守技术方案；各来源的字段映射和结算时间差需要合成及脱敏样例验证。

1. **先排除同源重复。** 根据操作身份与来源身份返回已有结果或跳过明确重复，记录原因并产生用户可见提醒。新文件中的新增行继续处理。
2. **检索共同订单号。** 只用已验证的同一订单号作用域和值查找跨来源候选；不同账本不能匹配。缺少共同号或出现多个可能目标时保留候选。同一订单组内若有金额、日期等关键事实不清或来源自身冲突，整组暂不自动关联；批次中其他独立组可以继续入账。
3. **检查其他事实。** 比较币种、金额及方向、交易完成状态、资金账户与支付渠道的关系、订单/付款类型、可解释的业务日期与入账日期差异、现有同笔/不同笔决定及金额分配。微信显示银行卡 A 代扣且银行 A 有对应扣款，可以相容；微信余额付款、银行卡向微信充值可能是两次资金事件，不能仅凭号相同压成一次。
4. **计算影响预览。** 核心计算关联前后个人消费、逐账户变动、已匹配与待匹配金额。纯补证据的变化应为零；已有两个正式账目时，若确认重复影响，需要在一个提交单元中退出多余的有效金额并迁移引用。任何超额分配、后续退款/报销依赖冲突或无法解释的金额差异都停止自动应用。
5. **提交时重查。** 在同一原子提交单元内检查来源身份、目标版本、订单号映射版本、既有关系和分配额度；并发导入若已建立关系，返回已有结果。只在唯一目标、事实相容且所有不变量成立时自动关联；否则保存核对项，不以旧预览盲写。

“其他事实不冲突”不是只检查金额相等。费用、部分付款、退款、充值与消费、失败后重试等场景可能共享订单引用，却代表不同金额事件；本方案默认进入核对，直到有经验证的专门规则。

## 4. 写入结果与可追溯性

自动关联由 finance-core 产生有类型的“同笔”关系，记录两端来源、共同订单号的作用域与原始值、字段映射版本、其他相容证据、规则版本、应用时间及操作标识。来源记录仍各自存在；关联本身不增加消费或账户变动。

导入结果至少区分：新增账务影响、只补来源/自动关联、明确重复跳过、待核对及失败。明确重复的跳过必须提醒用户；自动关联建议在结果摘要和明细中显示依据、关联目标与金额变化，方便用户发现误匹配。纠正自动关联走可追溯的更正/撤销操作，重新计算有效影响，不直接删历史来源。

核心必须维持以下不变量：同一业务消费只保留一份有效业务金额；同一真实账户扣款只保留一份有效账户变动；来源证明不占用付款额度；跨来源关联不得把银行卡代扣与微信零钱消费误判成同一账户变动。两条来源各自有正式账目时，列表合并与统计合并必须同一提交完成。

## 5. 与批次部分入账的关系

已核清且与其他草稿无依赖的记录可以先入账。共同订单号候选涉及的来源、可能被合并的账目及其分配构成一个相关提交单元；在未确定关系或版本冲突时，保留这一单元待核对，**不阻断**批次中其他独立记录。金额或日期不清的来源同样留待核对。批次结果分别保存各单元的完成状态，不能把整批只标为成功或失败。

单元的具体划分、部分失败重试和取消后的撤销路径仍是技术待验证项；已确认的业务要求仅是独立可靠记录可先入账。

## 6. 最小验证矩阵

| 输入 | 预期 |
| --- | --- |
| 同一提交请求重试 | 返回原操作标识及结果，无新影响 |
| 同文件重传或重叠导出中同源稳定交易号 | 明确重复自动跳过、留痕并提醒；新行正常处理 |
| 微信与银行共享同一已验证作用域的稳定订单号，银行代扣、金额方向与状态相容 | 自动关联，保留两份来源，只计一次消费及一次银行变动 |
| 同日同额但不同订单号 | 不因金额日期自动合并；两笔可保持独立 |
| 文本相同但订单号语义/作用域不同 | 不自动关联，展示候选或无匹配 |
| 共同号但微信为余额付款、银行为充值，或金额/状态冲突 | 不压成一笔；相关单元待核对 |
| 共同号对应多个目标，或已有“确为不同笔”决定 | 不自动覆盖既有决定，进入核对 |
| 两端已分别入账、确认后需消除重复消费或扣款 | 原子计算并校验影响；有依赖冲突时停止自动应用 |
| 并发导入相同订单 | 最多一份有效业务金额和账户变动；后到操作返回已有关系或冲突 |
| 同批另有金额/日期不清的独立行 | 确定行可先入账，问题行待核对，批次呈现部分完成 |

## 7. 2026-09-24 合成隔离验证结果

在 Node.js 24.19.0 下运行[可丢弃的内存实验](../../../experiments/finance-cross-source/README.md)：

```powershell
node .\experiments\finance-cross-source\verify.mjs
```

结果：脚本断言通过。共同稳定订单号且事实相容的微信/银行两来源得到一笔事件，消费 `3500` 分、银行卡变动 `-3500` 分；反向导入顺序结果相同。同源重传被跳过并产生提醒记录，同一请求重试返回原结果而不重复提醒。不同订单号的同额消费保持两笔；相同文本但订单号作用域不同不自动关联。金额冲突、多目标歧义及日期不清进入核对，独立的 2000 分消费可在同批先入账。两个既有单来源事件在模拟的旧状态中合并后仍为 `3500/-3500` 分，并保留旧标识别名。两个同版本预览依次提交时，后者被判过期；重评估后只跳过重复来源。

实验中发现并修复一处规则漏洞：同一订单组的一条来源日期不清时，原型会先提交另一条来源。现将整组保留待核对，同时允许其他独立订单组入账；相同处理也覆盖同组来源自身事实冲突。该发现已写入上面的判定流程。

**验证边界：**输入是预先归一化的合成对象，不是微信或银行实际导出；仅模拟单进程版本冲突，不证明跨进程并发、数据库事务原子性、崩溃恢复或 DSH 接入。跨日期结算窗口、订单号字段映射、退款/报销等后续依赖、同源状态更新和完整业务范围仍待验证。实验不进入 `plugins/`，V3 整体验收未通过。
