# 具体对象模型与跨入口合并

日期：2026-09-23。状态：技术讨论提案，尚未冻结字段、表结构、自动匹配门槛或复式分录方案。本提案细化[对象模型](domain-model.md)、[统一草稿与提交校验](drafts-and-posting.md)和[导入与核对需求](../requirements/import-and-reconciliation.md)。

## 一条核心规则

来源记录保存“看到了什么”，正式账目保存“这是什么业务”，账户变动保存“哪个真实账户改变了多少”。消费统计读取有效的业务金额，账户余额读取有效的账户变动。来源记录、关系和操作记录都不直接累加金额。同一笔业务可以有多份来源；同一真实账户变动也可以有多份来源证明。

六类对象是逻辑边界，不要求各对应一张数据库表。所有引用都要约束账本归属；精确金额带币种，日期保留原始精度。

| 对象 | 保存什么 | 不承担什么 |
| --- | --- | --- |
| 来源记录 | 标识、账本、入口、原文或附件引用及位置、采集时间、可选批次、来源机构及归属范围、外部交易号、原始状态、解析版本和字段候选。自然语言原话与表单输入也有来源定位。 | 不直接成为消费或账户余额；原文不因人工修正而改写。 |
| 正式账目 | 标识、账本、已确定的业务类型、业务日期及精度、业务金额与含义、币种、商户或对象、分类标签备注、关键字段选定值及其来源/确认依据、冲突与待补信息、有效状态和版本；用途待补时业务类型、业务日期和业务金额可暂缺。可以只有已确认消费，也可以只有用途待定的账户事实。 | 不把一笔付款、一笔消费、一个来源强制视为同一对象；不因来源数增加而增加金额。 |
| 账户变动 | 标识、所属账目、真实资金或负债账户、带方向的精确金额、币种、发生/入账日期及精度、确认依据、有效状态和版本。 | 不把支付渠道当账户；不以银行余额快照冒充交易变动；不自动解释消费用途。 |
| 金额分配 | 标识、分配类型、来源金额池、目标对象、分配金额、币种、依据、状态和版本。业务用途拆分、付款匹配、退款分配、往来结算是不同类型。 | 不把同一笔钱在同一用途池内重复占用；不把“证据证明了全额”误作全额付款分配。 |
| 关联关系 | 标识、有类型的两端引用、方向、候选/确认/拒绝/撤销状态、依据、确认者或规则版本及时间。涵盖来源证明、同笔判断、明确不同笔、事项归组和业务关联。 | 金额关系只引用金额分配，不另存一份可独立变化的金额；候选关系不改变报表。 |
| 操作记录 | 操作标识、账本、可信操作者及入口、意图、幂等标识和请求摘要、目标版本、变更前后或可重建差异、对象引用、结果、时间及更正/撤销关系。 | 不作为银行交易，不参与统计；此处不预先选择事件溯源架构。 |

“业务金额”必须注明含义。还款 1,020 元中本金 1,000 元、利息 20 元各有用途分配；只将利息计入相应支出。未拆分账目可视为一个完整用途分配项，汇总时不能再加父金额。用途未知部分单独展示。账户变动的正负号表示该账户账面余额增加或减少；资产与负债的汇总方向由账户类型决定，例如信用卡消费使负债增加 600，银行卡还款使资金减少 600、负债减少 600，但还款本金不再产生消费。

## 关系与额度

一条来源可能包含多笔账目，一笔账目也可能有多条来源。账户变动由一个有效账目拥有；若一次银行付款覆盖多笔消费，保留付款账目及其唯一账户变动，通过付款匹配分别连接消费账目。简单的一笔消费可直接拥有付款账户变动，但账户变动与消费金额仍要有一份逻辑付款分配；一对一分配是否独立持久化留给存储设计。来源证明尽量定位到具体字段、用途分配或账户变动，而非笼统地把整份文件视为所有字段的依据。

各类金额分配分别校验：业务用途分配合计加待定部分等于其业务金额池；一笔付款的有效匹配额不超过付款额，目标已匹配额不超过待匹配额；退款分配不超过本次退款和原业务的可退余额；往来结算不超过可用于结算的付款部分和目标未结金额。混合业务先拆明本金、利息、消费等用途，再校验后续分配可用额度。转账的两个账户变动是同一次内部资金转移，不能各当成一笔对外付款。

“来源证明”不消耗金额池。微信和银行如果都描述同一次银行卡代扣 35 元，可以各自证明全额，但只存在一条有效银行卡变动。银行扣款若其实是向微信零钱充值，随后微信零钱消费，则是两次不同资金事件，应保留内部转账与钱包消费。

## 自然语言先记，银行流水后到

例：“昨天午饭 35，用微信付的。”按已确认的待补入账方向，先保存自然语言来源 S1、消费账目 T1 和消费用途 35 元。微信仅作为支付渠道；真实扣款账户未知，暂不创建账户变动。如金额、日期或重复身份存在阻断歧义，仍先留草稿或核对项。

后来导入银行卡扣款来源 S2。匹配不能只看同日同额，需要核查账户、方向、实际状态、日期精度、商户、订单号和现有匹配。证据充分且符合已接受规则，或经用户确认后，S2 关联 T1，只补一条该银行卡变动 M1=-35，并将其 35 元付款额度分配给 T1 的消费金额。即使 M1 直接归属 T1，逻辑上也要校验这份付款分配；一对一场景可由核心推导，不能再产生第二条账户变动。消费仍为 35 元，银行卡变动为 -35 元。再导入微信明细 S3，若确认是同一银行卡代扣，只增加证明和缺失字段，结果仍为 35/-35。重复导入或提交重试复用来源/操作结果，不能重复创建有效影响。

如果 T1 早已明确银行卡并含有 M1，S2 只为 M1 增加证据；不能再创建 M2。相同金额日期但无法确认身份时保留候选。用户确认“两笔不同交易”的决定也要保存，避免反复建议合并。外部交易号的唯一性必须结合来源机构、账户或来源归属范围判断，不能跨机构当全局键。

## 两边都已入账时

银行来源也可能先独立形成用途待定账目 T2，拥有 M2=-35。确认 T1 与 T2 是同一业务前，消费报表为 35，银行卡报表为 -35。建议保留 T1 的身份和人工分类、标签、备注，将 M2 及其来源关系迁到 T1；T2 标记为被合并并指向 T1，历史引用仍可追踪。合并前后两项统计都不变。

若 T1、T2 各自已经贡献消费 35 或各有同一真实银行卡变动 -35，合并必须使重复的影响退出有效统计，并显示修正预览：消费 70 可变为 35，银行卡 -70 可变为 -35。不能只隐藏 T2 的列表行，却仍累计其分配或账户变动。被替代对象和原关联保留在历史中。

合并在一个提交单元内检查 T1/T2、来源、变动、分配与核对项的版本，迁移关系后重新校验额度和账本归属；任何超额或后续依赖冲突都阻断提交。被合并指向不能形成循环。已有退款、报销或结算时尤其需要检查迁移后是否重复占用金额。

## 部分匹配及冲突

自然语言“聚餐共 100 元”后只找到银行卡付款 60 元：消费保持 100，已匹配付款 60，待匹配 40；不凭差额虚构现金扣款。后来找到另一真实付款 40，再补其账户变动并匹配。反过来，一次银行卡扣款 100 对应餐饮 60 与日用 40：只保留一条 -100 的账户变动，用两条付款匹配连接两笔消费；两笔消费合计 100。

自然语言消费 35 与银行扣款 30 有差异时，保留两份证据及冲突。选择可以是明确更正消费、部分匹配、确认不同笔或继续待核对；系统不能暗自创造折扣、手续费或另一付款。银行来源证明扣款金额，用户输入可能更能说明消费用途，不存在对所有字段统一适用的“银行优先”。

退款是独立的实际资金与业务事件，以退款分配指向原消费；原消费行的“已退款”状态不能再产生第二次退款金额。

## 操作与撤销

幂等标识识别一次提交意图，来源身份识别同一证据，账目和账户变动标识识别有效金额事实，三者不可互代。提交时再次校验来源身份、版本和分配额度，不能只依赖预览。

撤销只补来源的操作时，移除该证明的有效关联，保留原手工账目。若操作还新增账户变动，撤销预览应说明该账户将重新待补；若变动已被其他证据支持或已被结算依赖，则重新评估，不能按批次删除。撤销合并需要保留原身份与迁移明细；出现后续退款、结算或编辑时先处理依赖，不机械恢复旧快照。





## 待补账目的正式状态（方向已确认）

已确认允许两种仅确认部分事实的正式账目：消费已确认但真实账户未知；真实账户扣款已确认但业务用途未知。前者进入消费分析，后者进入该账户流水；未知部分单列。正式入账不等于已核对完成。以下四格状态及字段约束是该方向的技术细化，仍待样例验证。

账目的确认状态分两个维度计算，不保存一个可被任意改写的“已完成”布尔值：

| 已确认业务金额 | 已确认账户影响 | 正式处理与展示 |
| --- | --- | --- |
| 无 | 无 | 仅保存来源与草稿；不产生正式账目或金额。 |
| 有 | 无 | 正式账目有业务用途分配；消费等报表按其业务日期计入，账户待补，资金余额不受影响。 |
| 无 | 有 | 正式账目持有账户变动；账户流水计入，业务用途待定，消费/收入/往来不猜测。 |
| 有 | 有 | 两种事实分别计入；已匹配金额与差额由付款分配计算，不能只因两维都有值就显示“已核清”。 |

“无”指没有可确认的该类事实，不等于金额为零。关键金额、方向或日期冲突时，先留草稿或核对项，不把模型候选写为正式事实。已确定业务金额但分类未知可用未分类；已确定银行卡扣款但用途未知不得设成“未分类消费”，否则仍然偷偷把用途定成了消费。待处理、失败或取消的交易也不能作为已完成账户变动。

正式账目上的业务金额可暂缺；账户变动上的账户必须是真实且明确的账户。来源原文、用户输入、已接受规则、模型候选及用户默认值分别保留为字段依据。人工确定的分类、标签和备注不会因后续导入而自动被覆盖。

## 金额不重复的不变量

建议核心以三种独立结果计算，而不是以正式账目的记录数计算：

1. 业务结果：按查询口径汇总有效且已确认的业务用途分配。未拆分账目逻辑上也有一项；正式账目展示的总额不再与分配项相加。退款、报销承担额通过已确认的业务关系调整个人消费口径，不改写实际付款历史。
2. 账户结果：按账户汇总有效账户变动。一个外部真实扣款在一个账户上至多有一份有效变动；多条来源可以证明它。银行扣款与钱包余额扣款若确属两次真实变动，则要保留两份并解释其资金路径。
3. 对应结果：每条有效付款分配占用一份可用于该用途的账户变动额度，并指向确定的业务用途金额。信用卡新增负债可支持原消费；转账收款端不能再作为一笔对外付款。所有有效分配不超过该变动可用于当前用途的金额；业务侧也不超出其待匹配额度。对应关系改变覆盖状态，不再产生业务金额或账户变动。

上述“同一真实扣款”的判断不能仅由金额日期唯一索引完成。有可信的来源交易标识时按来源机构及账户归属范围约束；没有足够标识时通过核对确认，并在操作记录中保存依据。候选不能触发合并。用户确认不同笔时，记录排除关系，使同金额的独立交易仍可入账。

来源身份去重、操作幂等、真实影响去重分别执行：同一文件重传不应复制来源事实，同一次提交重试返回原结果，两条不同来源描述同一付款不应复制账户变动。三道检查不能互相替代。

## 合并命令的最小结果

核心“确认同笔”操作接收两个账目标识、证据/人工选择、预期版本和幂等标识；核心计算目标账目、保留或退出的有效影响、需要迁移的来源与金额分配、冲突及报表差额。调用方不能直接提交“把 T2 设为已合并”来跳过金额校验。

| 合并前 | 合并提交的有效变化 | 合并后 |
| --- | --- | --- |
| 消费 T1=35，账户待补；银行 T2 用途未知，M2=-35 | M2 归入保留账目，建立 35 的付款对应；T2 成为历史别名 | 消费 35，银行 -35，待匹配 0。 |
| 消费 T1=35 且已有 M1=-35；导入来源 S2 描述同一 M1 | 只增加 S2 对 T1/M1 的证明 | 消费 35，银行 -35。 |
| T1/T2 各有效计了同一消费 35 或同一真实扣款 -35 | 确认哪份事实保留，重复影响退出有效口径，迁移依赖并记录修订 | 相应 70/-70 修正为 35/-35；历史操作仍可查。 |
| T1=35，S2 明确扣款 30，尚无其余付款依据 | 保留金额冲突或确认其中 30 的部分匹配 | 消费仍 35，已匹配 30，待匹配 5；不凭差额造扣款。 |

合并预览同时显示业务统计、各账户余额影响、付款覆盖、退款/往来额度与待补项。应用时在同一事务内重新检查对象版本、账本边界、来源身份和分配额度。已结算或已退款的历史账目可能无法直接合并，应返回冲突及可核对的处理路径。被合并标识保留别名映射，以便历史链接、操作日志和外部引用定位到保留账目。

## 与报表时间的关系

业务日期、账户发生或入账日期、操作确认时间分别保留。后来匹配银行来源可能补齐真实付款日期，但不能默默把原消费归属月改成银行入账月。若用户明确更正原消费日期，应产生可追溯的修订，并在按认知截止时间查询时保留旧认知。银行流水不完整时，账户页只能给出覆盖范围内的变动或有依据的余额，不能由单笔消费推断完整账户余额。




## 六类对象的同笔实例

以下标识只用于说明对象关系，不是数据库字段或 API 名称。金额单位为元，正式存储使用精确金额及币种。

| 时点 | 对象实例 | 本次有效金额变化 |
| --- | --- | --- |
| 用户说“昨天午饭 35，微信付” | 来源 S1 保存原话及“昨天”的输入参考时间；账目 T1 保存已确认消费、归属日期和餐饮分类；业务用途分配 A1 将 T1 的 35 指向消费；来源证明 R1 连接 S1 与 T1/A1；操作 O1 记录创建依据和版本。 | 消费 +35；任何真实账户 0；待补账户 35。 |
| 后来导入银行卡扣款 35 并确认同笔 | 来源 S2 保存原流水、交易标识及位置；账户变动 M1 将银行卡记 -35，归属 T1；付款分配 A2 将 M1 的 35 额度指向 A1；来源证明 R2 连接 S2 与 M1，确认同笔关系 R3 记录判断依据；操作 O2 记录本次补全及旧新版本。 | 消费 0；该银行卡 -35；待补账户 -35。 |
| 再导入同笔微信明细 | 来源 S3 保存渠道原文；证明关系 R4 指向 T1、M1 或具体字段；操作 O3 记录补证据。 | 消费 0；该银行卡 0；待补账户 0。 |

A1 与 A2 都写 35，但分别回答“这笔业务是什么”和“这笔钱从哪里支付”，报表不将二者相加成 70。S1、S2、S3 是三份证据，不是三笔消费。O1、O2、O3 是三次操作，不是三笔资金流。若微信实际上扣微信零钱，须根据真实资金路径重新核对 M1/R4，不能为了保留上述示例而压掉确实发生的钱包变动。

每次应用结果至少返回本次导致的业务金额变化、逐账户余额变化、待匹配金额变化、创建/复用/退出有效口径的对象标识，以及仍需核对的问题。上述 O2 的消费变化必须为 0；重试 O2 返回同一操作结果，不能再次返回一笔新的银行卡扣款。导入预览与实际提交使用同样的影响计算，提交时因版本或匹配变化而过期则重新评估。

## 待验证场景

不同导入顺序得到相同有效金额；同日两笔同额能够保持独立；并发导入与重试只有一次有效影响；一笔消费对应多次付款；一次付款匹配多笔消费；两笔已入账后合并消除重复；退款不当作重复付款；超额分配阻断；只补来源的撤销保留人工账目；跨账本关联拒绝。当前未进行代码或数据库验证。
