# 技术设计：统一草稿与提交校验

状态：候选方案，未实现或验证。已确认多个记账入口、两种待补正式账目、明确重复的自动跳过与独立记录的批次部分提交；其他自动提交条件和依赖记录的处理仍是建议，尚未逐项确认。

依据：[多入口解析](parsing-and-import.md)、[记账需求](../requirements/import-and-reconciliation.md)。

## 1. 草稿的职责

草稿是对一次业务操作的结构化提议，承接文件、截图、自然语言或表单输入；它不是正式交易，也不是把所有金额缺失记录硬塞进统一交易表。

同一输入可能产生多个草稿。操作意图区分新增账目、补充来源、修改账目、建立关系，避免发现重复时仍新增消费或把用户更正意图当新增。

核心负责评估哪些事实可确认、哪些影响可生效。不能用一个全局置信分同时决定金额、分类、账户和退款关系。

## 2. 草稿结构候选

| 信息组 | 候选内容 | 用途 |
| --- | --- | --- |
| 操作上下文 | 草稿标识、版本、账本、入口、操作类型、目标记录 | 固定写入范围并区分新增/修改/关联 |
| 来源证据 | 文件行/表格单元格、图片区域、原始文字、用户输入引用 | 支持核对和重解析 |
| 金额 | 精确金额、币种、收付方向、金额用途 | 区分消费总额、本金、费用等，不混用余额 |
| 时间 | 实际日期/时间、精度、时区、输入参考时间 | 保留日期事实及相对日期解析依据 |
| 业务含义 | 消费、收入、转账等类型，发生/待处理/失败状态 | 决定可生效的账务影响 |
| 支付信息 | 资金账户候选、明确账户、支付渠道、对象 | 渠道不等于资金账户 |
| 组织信息 | 分类、标签、可选事项、备注、金额分配 | 不必全部具备才可记账 |
| 关系提议 | 已有账目匹配、退款、结算候选及分配金额 | 关系未确认时不产生对应正式影响 |
| 校验结果 | 问题代码、涉及信息、影响范围、处理建议 | 驱动 UI 与 Agent 同样的核对流程 |

草稿结构不同于数据库表结构。暂不要求所有业务都存在相同字段，不为单笔表单伪造文件行号。

## 3. 每项值的依据

对关键字段分别保留选定值、原始值、来源引用以及依据类型：来源明确提供、用户明确输入、已接受规则、模型候选、用户设置的默认值。存在冲突时保留候选及冲突，不用最后一次输出无条件覆盖。

状态至少表达已确定、未知、存在冲突；置信提示仅辅助展示，不构成自动入账的唯一条件。默认日期或账户需标为默认来源，可修改；截图缺失年份不以导入年份伪装成原始事实。

原始证据保存与可审计更正分离；后续人工选择不能销毁原始依据。

## 4. 核心评估的三种结果

1. 可提交：本次操作必要事实齐全、没有未解决的阻断问题。
2. 可提交但需补充：事实足够支持部分明确影响，剩余不确定性单独保留且不污染其他报表。
3. 暂不可提交：金额、方向、日期或操作目标等必要事实存在歧义，或提交会重复统计、越界、超额分配。

“不需要新增”作为操作结果单独表达：已确定同一来源且没有变化时跳过；补充来源或来源状态更新不增加第二笔消费。

草稿生命周期与问题状态分离：编辑中/已提交/已取消表达生命周期；是否存在未补信息和是否允许提交来自当前校验。已提交记录可仍有核对项，但不是永远占据草稿状态。

可提交不等于无条件自动执行：核心输出就绪程度，另由明确的自动提交规则决定是否执行。模型只能提出事实和操作，不能通过设置 ready=true 绕过校验。

## 5. 校验矩阵提案

| 情况 | 处理建议 | 正式影响 |
| --- | --- | --- |
| 明确消费金额、方向、日期与账户，分类未知 | 可提交，分类为未分类 | 计入总消费及该账户变动，不漏掉金额 |
| 标签、事项、备注缺失 | 可提交 | 不影响账务正确性 |
| 明确消费，账户未知 | 可提交待补充 | 计消费，不假定任何银行/零钱账户变动；账户完整性提示 |
| 明确某银行扣款，业务类型未知 | 保存已确认账户变动，类型待定 | 计该账户资金变动，不猜消费、收入或债务结算 |
| 金额不清或方向冲突 | 保留草稿先核对 | 不进入正式金额统计 |
| 截图日期/年份缺失且无明确规则可补 | 保留草稿先核对 | 不编造月份进入趋势统计 |
| 用户设置当日默认且输入未指明日期 | 可按该默认评估并展示日期 | 日期依据为用户默认，不作为来源原文 |
| 高度相关的重复候选未解决 | 阻断新增路径，保留候选 | 不自动合并，也不先重复计消费 |
| 只是弱活动归组候选 | 不阻断明确账目 | 不自动创建金额关系 |
| 修改目标不唯一 | 先定位目标 | 不新增替代修改 |
| 关系分配超过余额或跨账本错误 | 阻断该操作 | 不部分写入有冲突的关系 |
| 来源为失败/已取消交易 | 留来源，不提交已完成付款 | 不计入实际消费和付款 |
| 明确待处理交易 | 保留待处理信息 | 不视为已完成资金变动 |
| 不支持币种 | 保留来源并提示 | 不混入当前单币种账本金额 |

重复阻断需明确规则和候选范围；相同金额本身不能令所有记录长期卡住。用户可选择确为不同交易，保存这一判断及依据，后续不反复提出同一问题。

## 6. 待补充不能变成暗中凑账

“消费已知、账户未知”和“账户扣款已知、用途未知”是两种不同的不完整记录。

前者可以出现在消费分析中，但不能让某个真实账户凭空减少。后者可以核对账户流水，但消费、收入及应收应付仍未确定。报告必须给出这些未定金额及影响；缺少完整解释时不承诺净资产已对平。

以后为已知消费补充账户，只补账户影响，不再增加一次消费；为已知银行扣款确认消费用途，只增加相应消费归类，不再减少一次银行余额。这要求各影响来自同一账目事实并在核心原子更新。

若底层选用完整复式分录，是否采用显式待清算科目需在对象/存储设计验证。不能用伪造的“未知银行卡”作为已核对资金，也不能自动把待清算余额算成确定应收或净资产。

还款或退款已到账但未明确关联时，可保留真实资金变动与未结关系；不得擅自减少某项欠款或原消费。具体汇总仍遵守报表中的待关联展示规则。

## 7. 已确认边界与提交策略提案

表单保存、对话明确记账指令、批次提交都调用同一核心评估与应用流程。

已确认：同一文件重试、或稳定来源交易标识能明确判定重复时，可以自动跳过、留痕并提醒；独立且已核清的批次记录可以先入账，金额或日期不清的记录留待核对，不阻断其他独立记录。

候选默认：明确单笔指令且没有阻断问题时，按已配置策略直接记录并返回摘要、待补信息和撤销入口；金额冲突等问题先追问。批量文件先展示新增/补来源/更新/跳过/待核对分组。分组和提醒的具体界面尚待设计。

已确认的部分提交只覆盖相互独立且已核清的记录。消费与退款、转账两端、拆分父子项、同一重复候选组等有依赖的操作建议形成一致的提交单元；具体边界仍待验证，不能为了部分成功破坏金额守恒或关系完整性。

批次结果持久化每个单元的操作结果和目标记录，重试只重做未成功部分。批次取消停止未提交操作，已成功部分另走撤销流程，不能显示整个批次像从未发生。

## 8. 候选命令与一致性约束

候选任务能力：创建或更新草稿、评估草稿、处理核对问题、应用一组操作、查询结果、撤销已应用操作。最终方法名和工具数量留待接口设计，不预先暴露每个内部步骤给 Agent。

评估输出：当前版本、动作类型、影响预览、问题及严重程度、待补项、允许动作。应用请求携带账本、目标版本、操作标识与已解决选择，核心提交时重新校验。

两个来源同时发现同一笔交易时，仅有前端预览去重不够；提交期间也要检查当前证据与已存关联。按有明确语义的来源标识约束重复，不能把相同金额/日期设为唯一键。

幂等标识对应一次提交意图；同一重试返回同一结果，不阻止用户合法记录另一笔相同金额交易。更正与追加证据保留操作者、时间和改动依据。

## 9. 三个入口例子

A. “昨天午饭 35，用微信付的”：日期依据输入参考时间；消费 35 可明确，微信是渠道。按候选策略可记录消费、账户待补；若后来明确扣某银行卡，再补账户影响。

B. 银行截图清楚显示某日扣款 35，但看不出用途：记录该账户扣款事实，业务类型待定；之后与 A 确认对应，形成同一账目的消费与账户影响，不累计成 70 元。

C. 微信文件随后出现对应交易：在来源和人工确认足够时只补充证据，不再次计数；若同日两笔 35 元仍无法区分，进入重复候选核对。

A 与 B 在匹配前可能各自保存部分事实。确认匹配时要合并有效影响并保留原标识的追溯，不允许合并过程重复增加消费或账户变动；这属于后续关键验证场景。

## 10. 待验证

字段依据保留；用户默认与原文区分；未分类纳入总消费；账户未知不影响真实账户；用途未知只反映已知资金流；补全不重复计数；两种部分事实合并；草稿与正式记录切换；更正目标歧义；多记录依赖部分提交；重复提交；预览过期；部分成功后取消与重试；仅补来源操作的撤销。

当前是纸面设计，未选择数据库模型或实现测试。两种待补正式账目、明确重复自动跳过并提醒、独立记录批次部分提交已由用户确认；其他自动提交条件、核对门槛与有依赖记录的批次处理仍需后续确认。
