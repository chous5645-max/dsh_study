## 10. 双插件职责

finance-core 保存预算版本、周期规则、计划实例、执行分配及场景参数，负责确定性预测与去重。finance-ui 提供预算页、日历/列表、预测曲线与场景切换。DSH Agent 负责提议周期规则、解释资金低点和交互式假设分析。

具体 DSH 调度接入未验证。计划持久化应独立于聊天；应用关闭期间如何补算计划、补发通知以及避免重发，需要后续集成实验。

## 8. 与双插件及已有模型的关系

finance-core 承载预付成本、押金结算、持仓变动和估值记录；复用既有账目、来源证据、结算分配和变更历史。各类资产内部规则独立，不能用一个万能余额字段隐含所有语义。

finance-ui 提供资产概览、押金/储值详情、持仓及估值说明。Agent 识别可能的充值/押金/投资记录、询问关键缺失信息，并解释资金去向；正式分类、分配与估值计算仍通过核心 Interface。

实体关系和 Interface 在范围完成后统一收敛；目前不创建实现模块或增加第三个插件。

## 分析查询的技术约定（迁入）

## 9. AI 分析与查询约定

核心 Module 返回计算结果与证据，不由 Agent 根据散落文本重新算账。查询结果建议携带范围、口径、修订号、数值、构成明细、待定金额和覆盖限制。

“这个月花了多少”默认解释为个人消费并明确标注口径，可同时给出实际付款摘要；“银行卡少了多少钱”使用账户变动。比较两个月时必须使用同一口径及一致认知截止时间，不比较两张不同版本的截图数值。

Agent 的解释分为已证实差异与可能原因。比如“餐饮增加 500 元”由核心证明；“因为社交变多”必须有分类、标签或用户上下文支持，否则只能作为假设。回答中的金额关联明细，仍不强制识别完整事项。

## 业务关系到对象模型

## 4. 统一业务关系提案

来源记录 → 记账记录 → 账户变动与分类分配。事项是记账记录之上的可选归组，不是导入或记账的前置条件。

经济事项可以产生应收或应付，并通过后续收付款逐步结算。报销、借贷、退款有各自的关系和状态，不能仅靠一个分类标签表达。

建议新增概念：往来对象、应收/应付事项、结算分配、报销事项、还款计划、原交易关联。

- 一笔事项可有多条来源记录、多项分类、多条账户变动。
- 一笔付款可同时包含自付消费、代垫和手续费。
- 一笔收款可结清多个应收；一个应收可分多次收回。
- 每次结算记录分配金额，防止重复结清或超额核销。
- 本金与利息分开：借入本金不是收入，归还本金不是消费；利息和费用按明确规则计入支出。
- 应收不是可用现金；报销资格不确定时应标记待确认，不自动计作确定可收资产。
- 退款与报销都可能表现为收款，但前者冲减原消费，后者结算垫付；必须区分。
- 计划和实际流水分开；到期不表示已经支付，报销申请不表示已经到账。
- 应收、应付和负债账户表达不能重复汇总同一余额；后续需用具体记账模型验证。

技术模型仍未冻结：需要以代表性案例评估复式分录及往来明细，避免用普通收支表堆标签承担所有业务。
