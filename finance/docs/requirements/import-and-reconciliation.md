# 批量导入、单笔记账与核对需求

已确认入口：微信/支付宝 CSV 与 Excel（表头可能变化）、银行截图、自然语言记账、单笔表单记账。具体文件变体、自动提交规则和异常交互仍待确认。

## 用户需要的能力

一次提交多份账单，查看每份资料的处理状态、新增记录、重复记录和需要处理的问题。银行截图可以单张或批量提交。自然语言和表单单笔记账是独立可用的入口，不依赖导入文件，也不要求用户按银行流水重新组织个人账目。

支持重复上传、导出期间重叠、多个来源描述同一次支付的情况；重复不能增加收入或消费，不同交易也不能因同金额而被误合并。

用户能定位原始依据、修正账户和分类、确认或拒绝关联。只有可靠记录才进入相应正式统计；资料不完整时说明覆盖范围。是否允许部分提交和默认自动入账程度仍待确认。

## 自动化的业务约束

来源明确的事实、AI 的候选推测和用户确认分别呈现。无法判断请客还是垫付时不自动创建债权；弱归组不改变金额；影响金额的关系需要明确依据。

减少重复核对，但不以虚构确定性换取自动化。人工修正不能被后续导入无提示覆盖。未知格式提示支持情况，不产生看似成功的错误账目。

## 可靠性与可追溯需求

失败后重试不重复记账，关闭聊天不丢失已保存结果。提交期间数据变化应提示重新核对；撤销导入应说明对已经关联退款、报销或还款记录的影响。

原始资料、正式账目、人工更正的来源可以追溯。金额和日期缺失不能由系统假装确定。多账本切换不能改变正在处理的导入目标。

## 验收场景

同一文件重导、重叠月份导出、渠道和银行卡同时出现消费、同金额不同交易、部分退款、手工记账后再导入、失败重试、核对后数据被修改、跨账本误导入、导入撤销后保留有效关联。

解析、标准化、去重证据、任务状态及事务方案见技术设计 [parsing-and-import.md](../technical/parsing-and-import.md)。


## 各入口的具体要求

微信和支付宝文件表头改名或换序时，应尽可能继续识别；无法确定时说明需要核对哪些列，不能静默错读金额或日期。

银行截图需要让用户对照原图核对识别结果。金额不清、年份缺失或账户不明时保留问题，不能编造；支持截图中有多条流水以及多张截图重叠。

自然语言支持新增和明确的修改意图；单笔表单直接可用，不要求用户先写一句话。缺少账户信息时，不把微信/支付宝渠道自动等同于余额账户。清晰输入应减少操作步骤，自动提交的具体条件另行确定。

先手工或自然语言记账，后导入微信、支付宝或银行资料时，可以为既有账目补充来源，不能重复计算。人工分类、标签和备注应保留；有冲突时展示差异。

## 待确认的入账体验提案

建议区分可直接入账、可入账后补充与必须先核对。缺分类可暂记未分类；明确消费但账户未知时可先保存消费并提示，不随意减少某个账户余额；明确银行扣款但用途未知时保留资金事实，不猜测消费。金额、日期或重复记录等关键歧义先核对。批量可靠部分可考虑独立提交，有关联的部分保持一致。细化方案见 [提交校验](../technical/drafts-and-posting.md)，这些策略尚未逐项确认。
