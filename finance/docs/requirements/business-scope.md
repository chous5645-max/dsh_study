# 业务范围与场景需求

状态：范围讨论稿，尚未划分优先级或版本。2026-09-22。

用户明确要求包含：消费分析、账户管理、负债、欠款、借钱、报销、退款。下面展开这些领域，并列出供讨论的相邻能力；候选能力不等于已确认需求。

## 1. 已确认领域及其场景提案

| 领域 | 场景与行为 | 需要回答的问题 |
| --- | --- | --- |
| 收支与消费分析 | 收入、日常消费、分类、标签、交易拆分、周期比较、商户与项目分析 | 钱花在哪里？实际由我承担多少？ |
| 账户管理 | 现金、银行卡、支付余额、信用卡；期初余额、转账、充值提现、手续费、余额核对与调整 | 钱在哪里？哪些余额有完整依据？ |
| 负债 | 信用卡、消费分期、个人贷款、房贷车贷；本金、利息、费用、账单与还款计划 | 欠多少？已还多少？何时到期？ |
| 借入与欠款 | 向他人借款、他人代付、部分还款、分次借还、约定利息、欠款减免 | 我欠谁？欠款由什么事项产生？ |
| 借出与应收 | 借钱给他人、替他人垫付、部分收回、多笔合并结算、无法收回 | 谁欠我？还有多少未收？ |
| 报销 | 个人垫付、拆分可报销与自付部分、申请记录、部分到账、驳回、核销、预支与退回余款 | 垫付多少？提交多少？到账多少？最终自付多少？ |
| 退款与交易更正 | 全额或部分退款、多次退款、跨月退款、退回不同账户、撤销与冲正、原交易缺失 | 原始消费多少？退了多少？净消费多少？ |

这里的报销功能定位为个人跟踪；是否对接企业审批系统需要单独讨论。欠款是尚未结清的义务，既可能来自借款，也可能来自信用消费、他人代付等，不另造一套重复账目。

## 2. 待确认的相邻范围

- 共同消费与 AA：代付、多人分摊、他人代我支付、合并结算；多人参与事项不等于多人共同登录使用应用。
- 押金、保证金、预付款、储值卡：支付时不一定形成最终消费，后续可退回、抵扣或损失。
- 预算与财务计划：分类/项目预算、储蓄目标、周期账单、订阅、已知还款与应收款的现金流预测。
- 投资与其他资产：基金股票、理财、定期存款、收益费用、估值及净资产；管理记录与估值不等于执行投资交易。
- 多币种：用户已明确暂缓，保留币种语义与后续迁移位置；不在当前范围实现汇率、换汇或汇兑损益。
- 已确认个人日常统一个人账本，以分类、标签和视图组织；保留独立账本能力。家庭共享后续迭代。
- 提醒：还款到期、报销未回、借款未结、订阅扣费和数据缺失；通知渠道与自动化方式另定。

## 3. 贯穿所有领域的能力

批量账单解析、截图与自然语言补录；保留原始文件与来源记录；跨来源去重和交易关联；分类规则与人工修正；交易拆分；搜索与明细引用；附件凭证；数据覆盖范围；变更历史、更正与撤销；导入导出、备份恢复；数据发送与隐私设置。

识别来源记录与经济事项是不同步骤。账单通常只能证明支付或收款，未必能证明借贷关系、报销资格或退款归属；AI 可以提出候选关系，不能把猜测当成已确认事实。

## 4. 统一业务概念与规则

来源流水、记账记录与可选活动事项分别表达支付事实、用户账目和活动归组。一个实际收付款可以对应多个用途，一项借款或报销也可由多次收付款结清。

本金往来不当成日常消费或普通收入；退款与报销到账需要分别解释；应收不等于现金；计划不等于实际发生。资产、负债和往来明细不重复汇总。

这些是业务含义和正确性要求。具体对象、字段、父子关系或多对多分配结构移入 [domain-model.md](../technical/domain-model.md) 与 [feature-integration.md](../technical/feature-integration.md)，尚未冻结。

## 5. 统计视角提案

| 视角 | 内容 |
| --- | --- |
| 资金流水 | 实际收付款与账户之间的流动，支持单账户和自有账户合并视角 |
| 个人消费 | 实际由本人承担的成本，说明退款、报销、代垫及跨期调整口径 |
| 资产负债 | 资金资产、明确确认的应收、投资等资产与负债；标识数据完整程度 |
| 往来结算 | 按对象、事项和到期日查看借出、借入、报销及未结余额 |
| 未来现金流 | 基于计划的还款、账单、预计收入与应收，区分已确认和估计 |

同一事项在不同视角呈现不同数值；所有视角必须能够解释其口径和回溯构成明细。退款跨期、报销尚未确认、坏账与减免的统计处理需要进一步讨论。

## 6. 用于讨论与后续验证的例子

1. 支付 1,000 元差旅，其中 800 元待报销、200 元自付。确认报销资格后形成相应应收；分两次收回 500 和 300 元。资金流出、个人消费、待收回金额分别展示。资格未确认或被驳回时另有状态及更正路径。
2. 借给朋友 2,000 元，先收回 500 元，之后收回剩余本金。借出与收回不是普通消费和工资收入。
3. 借入 10,000 元，偿还本金 1,000 元和利息 50 元。现金支出 1,050 元，负债减少 1,000 元，利息成本 50 元。
4. 信用卡消费 600 元，次月从银行卡还款；消费只计一次，信用卡负债和银行资金分别变化。
5. 购物付款 500 元，跨月分两次退款 100 和 150 元；保留原消费与退款记录，按明确口径展示净消费 250 元。
6. 聚餐付款 600 元，本人承担 200 元，另外两人各承担 200 元。后续收回 400 元结清代垫，不能重复算作个人收入。
7. 多来源记录同一消费，后续又有退款；关联后不重复消费，也不重复冲减。

## 8. 已确认的展示与自动关联原则

2026-09-22 用户确认：默认以账目列表与统计为主，事项视图是可选聚合。先形成可靠账目，再逐步关联成事项；不能强制 AI 为所有账目推断完整业务故事。

区分三个层次：来源流水保存渠道事实；记账记录表达账本中的记录和统计分配；事项将解决同一件事情的记录归组。来源流水与记账记录不要求一一对应，多对多匹配需记录分配金额，不能凭差额伪造银行流水。

自动化分层：

- 来源事实：金额、时间、交易标识、来源明确提供的原订单号，程序解析并保留证据。
- 候选推测：根据商户、时间和金额提出关联建议，不作为已确认事实。
- 用户意图：请客、垫付、报销资格、还款用途等，缺少依据时保持未知或等待补充。

弱关联仅用于组织和浏览，不自动改变金额、分类或应收应付。影响金额的去重、退款分配和借贷结算需要更严格的依据；模型置信度不能代替证据。关联应记录来源、依据及确认状态，并支持撤销。候选关联不得悄悄改变正式统计。

未确认关联不必阻断所有账目入账；影响基础字段或可能重复统计的异常需独立处理。对未决记录明确显示统计采用的现有分类或暂定口径，不宣称完整准确的最终个人成本。哪些情况允许自动处理的具体规则仍待定义。

案例：餐厅付款 200 元可先记餐饮 200 元，不自动拆分出朋友的 100 元或生成应收。后续收到朋友 100 元，仅凭时间相近不能确定属于 AA；可以提出候选，用户确认后再建立关系。用户不追求精细分摊时允许保留简化记账方式。

### 拆分与关联的业务需求

- 父子拆分：表达一笔记账内部的金额分配，父总额与子项不能重复统计。
- 事项归组：把多笔独立记录归到同一活动，不改变账务结果。
- 有类型的关联：表达退款、还款、报销到账与原记录的关系，支持一对多及多对多金额分配，避免使用单链限制真实结算。

实际到账退款拟新增记录并关联原消费；退款申请是状态，原金额记错是更正，两者不能伪装成到账退款。具体存储结构与跨期统计口径尚待后续确认。
