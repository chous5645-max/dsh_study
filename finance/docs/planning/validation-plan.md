# 需求验收与技术验证计划

当前说明：以下为早期候选验证路线，暂不作为版本范围或优先级。按用户最新要求，先完成 [business-scope.md](../requirements/business-scope.md) 的整体范围与场景讨论，再重排本计划；需要补充应收应付、借贷结算、报销与混合事项的验证。

V0 的[合成账务验收样例](v0-acceptance-cases.md)已整理为待业务验收的纸面预期，尚未完成业务验收。V1 已完成部分固定版本集成验证；V2 仅完成[单来源隔离实验](../../../experiments/finance-single-source/README.md)中的部分合成场景，V3—V5 尚未执行。V1 运行结果见[验证记录](../technical/dsh-v1-verification.md)。先确认产品范围，再用最小可复现实验验证风险。每阶段记录设计版本、环境/DSH 版本、输入、预期、实际结果、证据位置和后续决定。

## V0：需求验收样例与业务口径

准备脱敏或合成账单，涵盖普通消费、同文件重导、重叠导出、跨渠道同笔消费、转账、信用卡还款、部分退款和同金额不同消费。

手工给出预期交易及消费/资金流向结果。先讨论这些结果是否符合使用习惯。不要要求用户提供凭证密码或完整卡号。

通过条件：核心术语、账户深度、去重策略和已讨论的统计口径达成明确结论。未决口径保留为问题，不能由实现默默决定。

## V1：技术验证——DSH 两插件集成（部分完成）

固定版本，在隔离示例数据上验证：核心注册能力 → UI 调用 → Agent 调用相同能力 → UI 与回答引用同一明细。

已验证 Host 插件装配、共享服务、工具执行、运行期 Gateway Remote、早先的浏览器 SRC Connection RPC、Client Module 执行与 main Slot 诊断面板渲染、插件自有合成数据的重启恢复，UI 禁用时核心查询，以及核对摘要预填到 DSH 原生 Session 草稿。独立合成 TypeScript 工作区已生成严格 Remote 描述符与校验器；Node Client Remote 已挂载生成贡献，并经认证 Connection RPC 调用固定版 Host 严格接口。外部插件包的正式构建与 Typert Loader 注册、浏览器中的生成契约调用、真实模型调用、财务业务界面、文件上传、删除聊天后的账本保留、事件更新与结果跳转仍待运行验证。记录真实接口，不以文档推断代替运行证据。

通过条件：界面与 Agent 查询相同结果；账本不随聊天删除；禁用 UI 后核心可查询。暂不接真实金融数据。

## V2：单来源导入闭环（隔离实验部分完成）

实现一种已选格式、预览、提交、列表、分类汇总与持久化。用业务 Interface 验证幂等、提交中断重试与版本冲突。

通过条件：重复导入不新增交易；每个汇总可追溯明细与来源；人工预期和程序统计一致；重启后数据完整。

已用固定合成 CSV 跑通预览、提交、重导、重叠导出、查询和 JSON 持久化，并检查重试与冲突。实际微信/支付宝格式、正式业务 Interface、DSH 插件集成、跨进程并发及真实数据仍未验证；本阶段尚未通过整体验收。

## V3：多来源、账户与核对

加入第二来源，验证跨来源关联、转账、还款、退款以及人工核对。相同金额的独立交易不能误合并。

通过条件：样例中无重复消费；存在歧义时明确进入核对；修改与撤销保留来源；缺少完整流水时不伪造可信余额。

## V4：Agent 分析与工作台

围绕“钱花到哪里”“比上月多在哪里”“哪些记录还需核对”验证多步查询、说明和明细跳转。

通过条件：结论数值匹配核心结果；口径和范围可见；不会将账单中的指令文本当作业务指令；普通图表查询无需模型调用。

## V5：个人试用与迭代

经用户选择使用实际账单，验证备份恢复和日常更正。真实原始账单、数据库、密钥不进入 Git；实现前增加相应忽略配置。

观察指标：每次导入耗时、需人工核对比例、误合并与漏重复数量、分类纠正次数、分析结论的可核验程度。

正确性样例是硬性通过条件；性能和自动化比例在获得代表性文件后确定目标，不预设虚假的准确率承诺。
