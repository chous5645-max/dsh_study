## 提案，尚未冻结

- 核心业务契约见 [core-interface.md](technical/core-interface.md)：UI/Agent 共用类型化业务操作；提案与应用分离；核心校验版本、幂等及确认依据；方法名称和传输方式尚未冻结。

- 统一草稿与提交规则见 [drafts-and-posting.md](technical/drafts-and-posting.md)：字段依据分开，核心决定阻断或允许；缺分类可入账，账户或用途不完整仅确认有依据的影响。两种待补正式账目、明确重复自动跳过和独立记录的批次部分提交已确认；其他自动执行条件及有依赖记录的提交边界尚待确认。

- 分类、标签、事项细化见 [categories-tags-and-events.md](requirements/categories-tags-and-events.md)：主分类表达性质，多标签交叉筛选，事项归组具体活动；金额拆分与业务结算独立于标签。细节待验证。

- 押金、预付、储值和投资资产提案见 [assets-and-prepayments.md](requirements/assets-and-prepayments.md)；区分真实付款、消费成本、商户额度及资产估值。储值的充值记消费/使用记消费需明确规则，不能重复记消费和资产。

- 预算、周期计划与预测提案见 [budgets-and-planning.md](requirements/budgets-and-planning.md)：预算与现金付款分开，计划不自动入账，预测只计未执行部分，并明确收款场景和覆盖范围。

- 报表的跨期回看与报销申请待定展示已确认，见 D15、D16。其他报表细节，如历史报告版本、批准金额变化及退款与报销同时作用于同一消费时的处理，仍见 [reports-and-analysis.md](requirements/reports-and-analysis.md) 待验证。

- 核心拥有导入、统计计算与报表数据，UI 拥有交互、图表与排版。
- 本地运行与 SQLite 为技术候选；用户数量和版本范围待整体讨论后决定。多币种已明确暂缓。
- 账本独立于会话，保存来源记录与变更记录。
- 核心与 UI 同仓库，固定 DSH 版本，逐阶段验证。
- 父子拆分、事项归组与有类型的多对多关联为数据模型候选；具体结构尚未冻结。

- 具体对象模型与跨入口合并见 [concrete-object-model.md](technical/concrete-object-model.md)：区分来源、业务金额、账户变动、分配、关系及操作；“先自然语言记账，后导入银行流水”只补缺失影响或证据。D19 已确认一个可自动关联的条件；其他自动匹配门槛、具体对象边界仍为提案。

## 当前技术设计与验证重点

1. 将已确认的来源去重、共同订单号自动关联和批次部分入账落实为核心判定与一致性约束，按[来源身份与匹配方案](technical/source-identity-and-matching.md)验证反例。
2. 收敛来源、正式账目、账户变动、关系与操作结果的边界，验证重复影响消除、依赖提交及并发重试。
3. 补齐 V1 的正式插件包、浏览器严格契约、真实工具调用和导入文件链路，再决定稳定实现如何进入 `plugins/`。

## 验证中仍需回访的业务问题

- UI 主要放在 DSH 独立财务页还是侧栏？以批量核对空间与 DSH 扩展能力验证结果决定。
- 验证 [reports-and-analysis.md](requirements/reports-and-analysis.md) 已确认的原消费归属口径、历史快照与待定金额展示方式，并继续讨论其余报表例外。
- 批次部分提交中，有依赖或冲突的记录怎样作为整体处理；失败项如何重试、已提交项如何撤销？
- 分类是否需要多级、标签和消费拆分？
- 重复候选如何确认，人工决定如何长期保留？
- 文件保留、导出备份和模型数据发送偏好。
- 账本跨会话共享范围，以及账单分析结果的历史可复现程度。
