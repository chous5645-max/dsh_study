# UI 设计方向与首轮原型

日期：2026-09-23。状态：设计方向与待评估原型；页面布局和具体组件尚未由用户选定。需求依据为[导入、核对与自动化](../requirements/import-and-reconciliation.md)、[对象模型](../technical/concrete-object-model.md)及[已确认决策](../decisions.md)。本文件记录交互意图，原型使用合成数据，不代表账务实现。

## 设计理念

1. **账目是日常主视图。** 默认按账目列表与统计看钱的去向；事项只是可选归组。导入是补充事实和核对的工作流程，不要求用户把个人记账重新组织成文件行。
2. **来源与账务分层呈现。** 用户应能从每一笔账看到原话、文件行或截图区域；多份来源证明同一笔账时，界面显示来源增加，同时说明消费和账户变动没有重复增加。
3. **不确定性有明确位置。** 已确认消费但账户未知、已确认扣款但用途未知，分别显示待补部分。候选关联、失败交易、日期或金额冲突不得装作正式金额事实。
4. **处理前看影响，处理后能追溯。** 确认合并、部分匹配、更正或拒绝关联前，展示消费、逐账户变动和待匹配金额的变化；提交后保留来源与操作记录。
5. **核对针对问题，而非反复确认整笔账。** 用户优先处理会影响金额、账户或身份的问题。清楚的分类、标签和人工备注在后续导入时保留；自动化条件仍由核心规则决定。
6. **对话与工作台共享当前核对对象。** 用户可以就选中的来源和账目向 DSH Agent 提问，Agent 解释依据和提出候选；确认、金额计算与写入仍交给 finance-core。对话应能返回原核对项，不另建一套聊天记账逻辑。

## 先定流程，再拆组件

首轮设计问题：一次导入多份资料后，用户怎样快速分辨“新增、补来源、待核对”，并安全处理自然语言账目与后导入流水的同笔匹配？

主流程：选择资料或使用合成导入 → 查看每份资料与总体处理状态 → 进入待核对项 → 对照原始证据、既有账目和金额影响 → 确认同笔、保持不同笔、部分匹配或暂缓 → 查看更新后的账目与未解决事项。日常账目列表始终可返回，不用创建事项归组才能完成导入。

组件从这个流程提取，而不是先按数据库表拆：批次摘要、问题队列、原始证据、账目摘要、金额影响预览、决策操作区、账目列表入口。候选关系与已确认关系要有明显不同的视觉状态；消费变化和账户变化用独立数字呈现。

## 首轮固定样例

- 原有自然语言账目：“昨天午饭 35 元，微信付”，确认消费 35 元，真实账户待补。
- 导入银行扣款 35 元和微信明细：候选同笔。确认后消费变化 0，银行卡变化 -35 元；微信资料只补证据。
- 同日另一笔 35 元：展示“确为不同交易”，不能因金额相同自动合并。
- 聚餐消费 100 元，仅找到银行卡付款 60 元：可确认部分匹配，消费仍为 100 元，待匹配 40 元。
- 一条金额或日期有冲突的来源：保留待核对，不伪造正式变化。

所有布局变体使用同一批合成数据和同一套操作结果，便于比较信息层级，而非比较文案或颜色。

## 原型形态与三个布局假设

原型挂在已验证的 DSH Web Client main Slot，使用浏览器内存中的合成状态。单一页面以 URL 的 variant 参数切换三个结构明显不同的方案，并有底部切换条。刷新可恢复布局选择，账务操作状态不持久化。原型不调用真实入账接口，不上传真实账单。 核对工作台内保留上下文对话入口；当前侧栏回复使用合成示意，另可把所选条目的摘要预填到 DSH 原生会话，发送仍由用户决定。只读工具从同一份合成样例读取来源事实；真实模型选择并调用工具仍待验证。

- **A：并排工作台。** 左侧批次和问题队列，右侧证据、既有账目和影响预览；适合连续处理大量问题。
- **B：逐题核对。** 一次突出一个疑点，按“来源 → 已有账目 → 影响 → 选择”引导；适合偶尔导入、降低认知负担。
- **C：账目优先。** 以日常账目列表为主，来源和待核对信息作为展开的检查区；适合从已有账目出发理解补来源。

这是结构选择，不是最终视觉样式。原型需要验证：用户能否准确判断哪份证据已入账、何时会改变消费或账户、如何保留同金额的不同交易、处理后怎样回到原账目。后续由实际使用反馈选定布局，再整理正式组件和 DSH Remote 契约。

## 当前可交互原型

[DSH 导入核对原型](../../../experiments/finance-import-review/README.md)已实现 A/B/C 三种布局与上述合成场景；这不是已选定的正式 UI。使用一条启动命令在本机 DSH Web Client 的 main Slot 打开，浏览器内存中可以切换问题、预览影响、确认、更正、撤销、筛选资料和返回账目列表。

2026-09-23 的无界面浏览器检查：三种布局均渲染；variant URL 从 A 切换到 C，刷新后仍保持 C，方向键可往返切换；账目列表可返回核对页；将咖啡消费 35 元明确更正为 30 元时预览显示消费 -5 元，确认后汇总从 205 元变为 200 元，撤销恢复 205 元；微信资料筛选只显示相关线索。同笔场景同时显示自然语言、银行和后到的微信来源；确认同笔后消费仍为 ¥205、已确认银行扣款仍为 -¥160。再把聚餐 100 元中的 60 元匹配给银行扣款，待匹配额从 ¥205 降到 ¥110，消费与银行金额均不重复增加。检查使用合成状态，尚未选择布局，也没有验证真实导入、正式 Remote 契约或生产级可访问性。



## 对话融合的原型修正

首版原型先只检验了纯核对工作台；根据用户反馈，下一轮把“当前核对项的财务助理”作为共同交互层加入 A/B/C。侧栏展示正在讨论的账目、来源与金额影响，支持提问示意和返回核对操作；需要原生会话时切回 DSH 聊天，并明确带走当前问题摘要。侧栏的示意答复不是模型输出，不能据此声称真实 Agent 已接入或允许它直接确认账务。当前原型点击“带入 DSH 对话”会创建或复用项目工作区中的财务会话，用原生 SessionInput.setDraft 预填所选核对项、来源依据、当前预览选择和只读工具提示，并注明原型选择并非正式账务；不自动发送；已有未发送草稿不会被覆盖。DSH 侧栏的“财务工作台”入口可返回原核对项。浏览器已验证草稿可见、示意提问、双向切换、选中状态恢复和草稿保护。正式实现仍需验证真实 Agent 在会话中调用工具、回答与核对项双向定位，以及权限与账本范围。



## DSH 会话与只读工具的验证边界

固定版 DSH 的空白会话若没有工作区，原生 composer 会处于不可用状态。原型在隔离 DSH_HOME 内为当前项目注册工作区并创建其会话后，浏览器实际读到了预填的“聚餐 100 元、银行扣款 60 元”草稿。新选择午饭核对项时，已有聚餐草稿保持不变。finance-core 原型包注册了 finance_review_case 只读工具，与 UI 从同一 mock-cases.json 读取金额与来源；工具 schema 可见且经工具执行管线返回了正确的 10000/-6000 分单位结果。隔离的 DSH_HOME 未配置模型 API Key，尚未执行模型自主选用工具或生成真实回复；工作台中的操作选择仍只存在浏览器内存，不应被 Agent 当作已提交账务。
